# 문구 점검 (UX 라이팅)

좋은 문구 = 멋진 말이 아니라 **사용자가 다음에 뭘 하면 되는지 알게 하는 말**.

## 원칙 (이 순서로 판단)
1. **분명함이 먼저, 짧음은 그다음.** 짧게 하느라 필요한 정보를 빼지 않는다.
2. **무엇이 + 왜(알 수 있으면) + 이제 뭘 하면 되는지.** 「실패」「완료」「오류」 한 단어로 끝내지 않는다.
   - 나쁨: 「전송 실패」
   - 좋음: 「보고서를 보내지 못했어요. 쓴 내용은 그대로 남아 있어요. 「보내기」를 다시 눌러 주세요.」
3. **안심시키기.** 입력한 내용이 남아 있으면 그렇다고 말한다. 저장됐을 수도 있으면 확인하라고 말한다.
4. **버튼 이름을 그대로 인용.** "다시 시도" 대신 「저장」을 다시 눌러 달라고.
5. **한 화면 한 목적.** 그 화면에서 할 일 하나만 앞에 둔다.
6. **익숙한 단어 의심하기.** 확인·완료·취소·유효하지 않음 → 무엇이 완료됐는지까지.
7. **부정 단어 줄이기, 사용자를 탓하지 않기.** 「잘못 입력했습니다」 대신 「날짜는 2026-11-02 처럼 적어 주세요」.
8. **소리 내어 읽어 어색하면 고친다.**
9. **기술 문구(영어 오류, 상태 코드)는 그대로 보여 주지 않는다.** 필요하면 쉬운 말 아래 「자세한 내용」으로.
10. **막히면 누구에게 물을지** 적는다(사내 도구라면 담당자 이름·채널).

## 읽는 사람별 말투 (처음 쓸 때 채워 두기)
| 화면 | 읽는 사람 | 말투 |
|---|---|---|
| 예: 고객용 페이지 | 손님 | 정중한 존댓말 |
| 예: 사내 도구 | 팀원 | 쉬운 해요체 |
| 예: 보고서·알림 | 팀장 | 숫자 먼저, 짧게 |

외국어 문구를 고칠 때는 후보마다 **한국어 뜻을 같이** 보여 준다.

## 절차
1. 대상 파일에서 문구를 모은다: `toast(`, `alert(`, `confirm(`, 오류 분기, 버튼 라벨, 빈 화면 안내.
2. 각 문구가 **어떤 동작에서** 나오는지 앞뒤 코드를 읽는다(같은 문구라도 상황이 다르면 다르게 쓴다).
3. 표로 보여 준다: 원래 문구 | 어디서(동작) | 문제 | 바꿀 문구 2~3개. 후보일 뿐, **고르는 건 사용자**.
4. 사용자가 고른 것만 반영한다("전부 적용"이면 첫 번째 후보로).
5. 반영 뒤 화면을 열어 실제로 어떻게 보이는지 확인한다. 배포는 사용자에게 알린 뒤에.
